## 1. 开发目标

在 Jetson AGX Orin 32GB 上，基于 `llama.cpp-omni` 二次开发一个离线 LLM/VLM Runtime 和设备故障辅助原型，形成以下闭环：

~~~text
GGUF 模型与版本校验
        ↓
Jetson CUDA Runtime 与自有 C++ Adapter
        ↓
文本/图片推理、流式输出、请求生命周期
        ↓
量化、KV Cache、Prefill/Decode 与资源评测
        ↓
本地 RAG、受限工具和故障报告
        ↓
Docker/systemd 演示部署与客户演示
~~~

## 4. 第1周：基线、模型选型和可复现构建

### 4.1 目标

把“一次运行成功”固化成任意团队成员可以重复的 Runtime 和模型基线。

### 4.2 任务

1. 获取带 Git 元数据的 `llama.cpp-omni` 个人 fork；
2. 记录 fork URL、branch、commit 和上游基线；
3. 比较当前源码快照与 fork，排除未记录差异；
4. 将 CMake include 修复迁移为独立 commit 或 patch；
5. 使用 out-of-source 目录重新配置和构建；
6. 编写统一环境/构建检查脚本；
7. 为每个候选模型建立 manifest；
8. 限定 2～3 个 LLM，使用统一 Prompt、context 和量化等级测试；
9. 固定主模型；
10. 实现 warmup + 至少 5 次重复 benchmark；
11. 输出 JSONL/CSV 和 Markdown 汇总；
12. 保存 tegrastats 原始数据和运行配置。

### 4.3 模型选型范围

最多测试：

- Qwen2.5-3B-Instruct Q4_K_M；
- Qwen3-4B Q4_K_M；
- 一个 3B～4B 备选模型。

只对最终主模型继续进行 Q8_0、高精度和 KV Cache 矩阵测试。

### 4.4 交付物

~~~text
third_party/llama.cpp-omni 或明确 fork 引用
patches/
configs/baseline/
scripts/build/
scripts/benchmark/
models/manifests/
docs/baselines/
~~~

### 4.5 验收门

- Runtime commit 可查询；
- 干净环境能按脚本完成配置和构建；
- 模型来源、revision、大小、SHA-256 和 GGUF metadata 可查询；
- 同一配置至少 5 次重复；
- Prompt/Generation throughput、TTFT/TPOT 或可获得的原始 timing 有统计；
- tegrastats 与每次运行有时间对应关系；
- 未实测数据不进入结论。

## 5. 第2～4周：C++ Runtime 与文本服务

### 5.1 目标

形成自有代码主体，使上层业务不直接依赖 `llama.cpp-omni` 内部对象或命令行格式。

### 5.2 第2周：接口和最小文本闭环

- 定义 `RuntimeConfig`、`GenerateRequest`、`GenerateResponse`；
- 定义 `RuntimeStatus` 和错误码；
- 定义 `EdgeOmniRuntime` 抽象接口；
- 先实现 `LlamaCliBackend` 原型；
- 配置化模型、context、GPU layers 和 sampling；
- 捕获 stdout、stderr 和退出码；
- 使用 fake backend 完成单元测试；
- 真实模型测试标记为 Jetson integration。

验收：统一请求能够调用 Qwen2.5 并返回结构化结果，单元测试不依赖 GPU。

### 5.3 第3周：模型生命周期和流式输出

- Runtime 初始化与 shutdown；
- 模型只加载一次；
- 流式 token callback/SSE；
- request ID 和日志关联；
- model info；
- runtime metrics；
- 上下文重置；
- 原始日志保存。

验收：连续请求不重复加载模型，流式首 token 可见，模型和请求可追踪。

### 5.4 第4周：超时、取消和错误处理

- 请求 timeout；
- cancel；
- 子进程或 Runtime 异常退出处理；
- context 超限；
- 模型不存在/hash 不符；
- CUDA/OOM；
- 正常停止；
- HTTP/JSON 服务原型；
- 如确有需要，记录 Ollama-compatible 字段范围。

验收：故障注入不会导致静默退出，错误均有稳定错误码和日志。

## 6. 第5～6周：量化、KV Cache 和性能

### 6.1 第5周：权重量化

只针对固定主模型比较：

- Q4_K_M；
- Q8_0；
- F16/BF16 高精度参考，前提是实际可获得且可加载。

固定：

- 模型 revision；
- tokenizer/chat template；
- Prompt 和目标输出；
- context、batch、ubatch；
- GPU layers；
- Flash Attention；
- nvpmodel 和散热条件；
- warmup 与重复次数。

输出：模型大小、加载时间、TTFT、TPOT、吞吐、RAM、温度、功耗和固定任务质量。

### 6.2 第6周：KV Cache 和长上下文

- F16 与 Runtime 实际支持的 Q8_0 等 KV 类型；
- 短、中、长 context；
- KV Cache 大小；
- Prefill/Decode；
- OOM 边界；
- 输出稳定性；
- Prompt cache 的启用/禁用条件。

验收：每项结论都有配置、原始数据和失败记录，不把上游工具能力表述为自研算法。

## 7. 第7～8周：VLM 图片与视觉指标

### 7.1 第7周：VLM 基线

- 选择一个实际支持的 VLM；
- 记录主模型、vision/mmproj 和其他模块的来源与 hash；
- 跑通单张静态图片；
- 支持设备照片和告警截图；
- 处理格式、大小、分辨率和损坏图片错误；
- 不进入实时视频。

### 7.2 第8周：统一接口和视觉性能

- `generate_with_image()`；
- 文本/图片统一 Request；
- image token；
- vision preprocess/encode time；
- TTFT、TPOT 和 total latency；
- 固定图片评测集；
- VLM RAM、温度和功耗；
- 流式输出。

验收：固定设备图片集能稳定输出，视觉耗时和资源有结构化记录。

### 7.3 实时语音团队边界

实时语音是项目最终能力，可以由其他员工负责：

~~~text
麦克风 → VAD/AEC → ASR → EdgeOmni Runtime → TTS → 播放
~~~

个人只记录实际参与部分：

- 若仅提供 Runtime 接口：记录接口设计；
- 若参与联调：记录 ASR 文本输入和流式 TTS 输出联调；
- 若未参与：仅列为团队后续模块，不作为个人成果。

## 8. 第9～10周：RAG、工具、Agent 和多 session

### 8.1 第9周：本地 RAG

- PDF、Markdown、纯文本和日志；
- 文档解析和切分；
- 本地 embedding；
- 本地向量索引；
- Top-K；
- 上下文拼接；
- 来源文档和片段 ID；
- 固定问答集。

验收：回答能返回真实来源；检索失败不伪造引用；正式运行不依赖云端 embedding。

### 8.2 第10周：受限工具和多 session

工具限定为 2～3 个：

- 文件搜索/读取；
- JSON/故障码查询；
- 日志统计或报告生成。

同时实现：

- input/output Schema；
- 权限根目录；
- timeout 和错误码；
- 工具审计日志；
- 基础 session 隔离；
- context reset；
- 请求排队和资源上限。

Agent 只做受控编排：判断是否检索、选择工具、生成带引用报告，不实现无限循环通用 Agent。

## 12. Definition of Done

一个任务只有同时满足以下条件才标记完成：

- 有代码、配置或脚本；
- 有可重复运行命令；
- 有成功和失败测试；
- 有原始日志或结构化结果；
- 有版本、模型和环境信息；
- 已知限制已记录；
- 不依赖个人未记录的手工步骤；
- 能解释上游能力和个人修改边界。

## 13. 状态管理

每项任务使用：

- `TODO`：未开始；
- `DOING`：进行中；
- `BLOCKED`：有明确阻塞；
- `DONE`：满足 Definition of Done；
- `DEFERRED`：移出当前周期。

每周结束记录：

~~~text
本周完成
真实测试结果
失败和风险
未完成原因
下周任务
需要团队协作的接口
~~~
