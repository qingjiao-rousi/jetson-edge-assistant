# 二次开发项目现状总结

状态日期：2026-08-04
审查对象：`vlmllm-main` 主项目、`third_party/llama.cpp-omni` 固定子模块、当前
工作树代码、测试、manifest、评测报告和原始 benchmark 目录。

项目背景：本项目基于开源 `llama.cpp-omni` 进行二次开发，Runtime 基础能力
属于开源上游而非本项目自研。完整项目最终实现“工业现场实时音视频全双工多模态交互，以及离线设备
知识检索与故障辅助”。本仓库继续负责既定的 Jetson Runtime、LLM/VLM、量化、
RAG/工具和部署主线；音视频采集、VAD/AEC、ASR、TTS、播放和全双工流控由
其他模块集成，不改变本仓库的开发顺序。

## 1. 结论

本仓库既定主线已完成 Jetson 基线、文本 Runtime 与服务、Q4/Q8 量化评测、VLM 单图
Runtime 和应用 API 四个阶段，当前进入第 9 周 RAG 阶段。最新完成项是
M9.1A：针对一份合成 Markdown 设备手册的离线 SQLite FTS5 关键词检索 MVP。

本仓库当前可准确表述为：

> 基于开源 `llama.cpp-omni` 完成 Jetson AGX Orin 端侧 LLM/VLM Runtime 二次开发，
> 已具备文本/单图推理、HTTP/JSON/SSE、模型资产校验、量化与 context 实测，
> 并开始接入带稳定来源引用的离线 RAG 检索。

当前还不能表述为“完整交付”或“生产可用”。RAG 尚未接入本地 embedding、向量
检索和 VLM 回答生成；受限工具、Agent、多会话、Docker/systemd、回滚、并发及
长稳均无完成证据。本仓库也没有完成音视频采集、ASR/TTS 和实时全双工联调，
不能把完整项目最终功能表述为当前已完成成果。

## 2. 已完成内容

### 2.1 Jetson、源码与构建基线

- 固定上游基线和个人 Runtime fork：
  `third_party/llama.cpp-omni@19cc26967140407efe34006a355ab445b35b16ac`；
- 完成 Jetson AGX Orin 32GB、L4T R36.4.7、CUDA 12.6、GCC 11.4、CMake
  3.22.1 环境审计；
- 完成 ARM64 Release + `GGML_CUDA=ON` 构建，修复 `mtmd` include 传递问题；
- 已建立 environment/build/runtime/model manifest 和模型 SHA-256 追溯；
- 文本基线确认 CUDA0 可用且 37/37 层 offload。

### 2.2 自有文本 Runtime 与服务

- C++ `DirectBackend` 直接链接 `libllama`，完成模型初始化/释放、生成、流式
  callback、context reset、timeout、cancel 和结构化 metrics；
- `RuntimeService` 提供 health、ready、model、metrics 及生成接口，支持
  HTTP JSON 与 SSE；
- `FakeBackend` 覆盖不依赖 GPU 的生命周期和服务契约测试；
- 已有固定 Qwen3 GGUF 的真实模型 integration 记录；
- 当前仍是单模型、单 context、单 active request，不支持真正的多 session 和
  并发队列。

### 2.3 量化、KV 与性能基线

- Qwen3-4B Q4_K_M 与 Q8_0 均完成固定协议测试：S/L/G 三种 workload，每种
  5 次有效 measured，共 15 次/模型，最终目录无失败记录；
- 记录模型加载、Prefill、Decode、tokens/s、UMA、温度和功耗；
- 部署决策冻结为 Q4_K_M 优先、Q8_0 作为高精度对照；
- 当前 DirectBackend 的 KV Cache 固定 F16/F16，未公开受控 Q8/Q4 KV 类型；
- 当前 KV 工作只覆盖类型、容量、context/OOM 和 Prefill/Decode 基线；请求间 KV
  生命周期复用尚未实现，文本请求仍在每次 Prefill 前清空 KV，VLM 请求在终止路径
  清空 KV；
- 已新增 M10.1 设计任务：先实现单热文本会话的 Token 级 LCP/Prefix 复用，再根据
  Jetson 内存和业务并发需求评估有界多 session；该任务当前为 `PLANNED`，无代码或
  性能验收证据；
- AI 辅助盲评在当前有限样本上无法区分 Q4/Q8 质量，不能外推通用质量结论。

### 2.4 VLM Runtime 与应用 API

- 冻结 Qwen2.5-VL-3B-Instruct Q4_K_M 主模型和 Q8_0 mmproj，完成大小、
  SHA-256、GGUF metadata 和 projection binding 校验；
- 实现 `ImageInput`、单图内存输入、JPEG/PNG/WebP 门禁、文件/大小/hash 资产
  校验和 `MtmdBackend`；
- 实现图片 HTTP JSON 传输、SSE `metadata -> token* -> terminal`、图片 token
  和视觉相关指标字段；
- 4096、8192 单图冒烟通过；8192 合成长手册 + 单图严格答案验证通过；
- 16384 完成一次 host-CUDA recovery 实验，32768 未执行且禁用；
- 单个常驻服务完成三张固定图片顺序请求，应用接口
  `POST /v1/diagnose/image` 又完成一次修复后的真实单图 HTTP/SSE 闭环；
- 8192 是当前开发默认 context。上述均为有限冒烟，不代表并发、长稳或平均性能。

### 2.5 RAG M9.1A

- 建立一份带版本、分类和内容 hash 的合成 AX-17 Markdown 手册；
- 按二级标题确定性切分，生成稳定 document/chunk/citation ID；
- 使用冻结 VLM tokenizer 记录真实 token 数；
- 使用 SQLite FTS5 建立离线关键词索引，支持 Top-K、原文片段和来源引用；
- 固定问题集中 5 个有答案问题命中预期 chunk，1 个无答案问题返回空结果且不

- 该阶段只有关键词检索，没有 embedding、语义召回、LLM/VLM 答案生成或真实
  设备手册质量评测。

## 5. 主要风险与文档判断

1. 当前主分支比 `origin/main` 领先 6 个提交，但 VLM、M8 API、RAG 及大量评测
   材料仍在未提交工作树中。审查开始时已有 95 个未跟踪路径和 12 个已修改路径，
   这是目前最大的可追溯性交付风险。
2. RAG 仅处理一份英文合成 Markdown、4 个 chunk，并采用关键词 OR 检索；尚不
   支持中文、PDF/日志、多文档、语义召回、重排或模型 grounding。
3. VLM 证据为固定图片的有限顺序冒烟；没有并发、连续长稳、真实设备图片集和
   生产质量阈值。
4. Runtime 仍是单 active request，`session_id` 非空会被拒绝；每次请求会清理 KV，
   尚无多轮/Prefix Cache 命中，因此不能声称多用户会话、缓存复用或并发服务能力。
5. Docker/systemd、鉴权、只读模型挂载、健康恢复、active/previous 回滚和日志
   轮转仅有设计，没有交付文件与运行证据。
6. 历史文档记录的是各里程碑当时状态，其中部分“待实现”已过期；当前状态统一
   以本文件为准，性能事实仍以对应冻结评测报告为准。

## 6. 下一步建议

1. 先把当前 M7～M9.1A 的代码、配置、测试、manifest 和报告按里程碑拆分提交，
   固定一个可复现的 clean commit；
2. 完成 M9.1B：多文档解析、本地 embedding/向量索引、检索质量集和无命中门禁；
3. 完成 M9.2：把检索片段和引用接入现有单常驻 VLM 应用 API，生成带来源的
   Markdown/JSON 故障报告，并防止无来源事实；
4. M9.2 验收后进入 M10.1：先完成文本单热会话、Token 级 LCP 的 KV Prefix 复用，
   再实现 2～3 个白名单只读工具和基础 session 隔离；
5. 只有 M10.1 的冷热一致性、分叉回滚、异常失效和 Jetson TTFT/Prefill 证据通过后，
   才评估 LRU/TTL、状态换入换出或多 sequence Prefix 共享；
6. 最后完成至少一种 Jetson 部署方式、异常恢复、回滚演练、回归与长稳，再评估
   是否满足阶段性交付。
